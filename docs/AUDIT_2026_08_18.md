# Audit — 18 August 2026

Read-only findings gathered while build tooling was unavailable. Nothing here has
been fixed; each item states what is true today and what it blocks.

## 1. Two firearm gamepasses sell for Robux and grant nothing

`Config.Gamepasses` offers:

| Pass | Gamepass id |
| --- | --- |
| `CivilianShotgun` | 1934518052 |
| `CivilianRifle` | 1934955986 |

Neither appears in `Config.EquipmentPasses`, which is the table
`LoadoutService:ApplyEquipmentPasses` reads to decide what a pass hands over.
That table contains only `Knife`, `ZKnife` and `Machete`.

Neither has a `Config.Tools` entry either. The full tool list is `Knife`,
`Machete`, `ZKnife`, `Handcuffs`, `Taser`, `MedicalBag`, `PoliceWarrantCard`,
`PAVA` — there is no firearm of any kind. Nor is there a firearm asset under
`server-assets/Tools`.

So a player who buys either pass receives an empty backpack. This is the same
fault the `EquipmentPasses` comment already records having found and fixed for
the ZKnife and machete passes, which "took 149 Robux for an empty backpack".

**Severity: highest open item.** Players are paying for nothing today.

**Options, in order of honesty:**

1. Delist both passes until the tools exist.
2. Build the two tools and wire them into `EquipmentPasses`.

Only the owner can delist a pass, so option 1 needs the account holder.

## 2. The firearms lockout has nothing to gate

The requested rule is that civilians keep a firearm but cannot equip it while no
firearms officer is on duty. Given item 1, there is no civilian firearm tool to
equip, so the rule cannot be implemented or tested until the tools exist.

The pieces it will need, all of which do exist:

- `Config.Roles.ArmedResponseOfficer`, division `ArmedResponse`
- `DutyService` to enumerate on-duty players and their roles
- `LoadoutService:prepareVisibleTool`, the single point every tool issue passes
  through, which is where an equip guard belongs

The guard must be server-side. A client-side check on `Tool.Equipped` is
bypassable and would be security theatre.

## 3. The MDT is department-aware in labels only

`MDTController.DEPARTMENT_UI` gives Police, Ambulance, Fire and Control their own
title, subtitle, accent colour and tile names. That much is real.

But every tile maps to one of four shared screen kinds — `Incident`, `Person`,
`Vehicle`, `Map`. Ambulance's "Patient records" opens the same person screen as
Police's "People", and Fire's "Risk information" opens it too. The screens have
been renamed per service, not rethought.

To make them genuinely different the *data* has to differ:

- Police: convictions, warnings, warrants, charge history
- Ambulance: presenting condition, treatment given, handover notes
- Fire: address risk information, hazards, access notes

That is server work as much as client work — each service needs its own record
shape and its own permissions on that record.

## 4. `renderCareers` is dead code

`DeveloperDashboard.luau` declares and assigns `renderCareers`, and never calls
it. There is no `addNav` entry for it, unlike every other page in the file. It
draws an "Emergency services" list of departments to join, which the Play page
now supersedes.

Roughly 240 lines. Safe to delete, but as its own change rather than folded into
unrelated work.

## 5. Civilian jobs page is empty because there are two jobs

`Config.Jobs` contains only `TaxiDriver`. `CIVILIAN_JOB_ROLE_IDS` contains only
`TransportOperator`. The page renders two tiles in a grid built for a full page
of them.

The render deliberately filters out anything without a working join path — "a
catalogue entry is a promise" — which is correct and should stay. The page will
only fill when more jobs genuinely exist.
